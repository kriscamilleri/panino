### Decisions

- **Index updates: the update hook plus an explicit after-sync call.** Every local write path
  (editor save, create, duplicate, delete, import, revision restore, phone capture, conflict
  resolution) reaches the index through the database's `onUpdate` hook on `notes`, so none of
  those call sites had to change. The changed rows are re-read by rowid or id in one
  `json_each(?)` query, 100 ms later, inside `runExclusive` so an open transaction has
  finished. `syncStore` also calls `remoteChangesApplied(dbKey, changes)` after every committed
  remote change set; that refreshes the synced note ids whatever the hook reports during a
  CR-SQLite merge. `noteChanged` / `noteRemoved` exist for callers that already hold the text.
- **When the index is built.** Lazily, by the first `ensure(dbKey)`: the sidebar asks when it
  first shows a database's Documents, and the build's first page waits for `requestIdleCallback`
  (1 s timeout), so first paint never waits. Pages of 250 rows by rowid with a task yield
  between pages. Parsing 5000 16 KB heads took 20 ms (median of five, Node 24); reading the rows
  from WASM SQLite was not measured on a large account.
- **What the index holds.** Canonical tags, their spelling per Document, and
  `parseFrontMatter(head).metadata` values unquoted (the API's `readProperties`); `tagCounts`
  counts every Document, including Trash. The filter leaves Trash out (`utils/tagFilter.js`,
  the API's `findTrashFolderId` rule), so the manager's count can be higher than the filter's.
- **Trash rule duplicated for now.** Search is moving the rule to `shared/trashFolder.js` in
  parallel; `utils/tagFilter.js` says to switch to it once it lands.
- **Filter UI.** While a filter is active, the sidebar shows a flat list of matching Documents
  (title, chips, space and folder path, newest edit first, "Show more" per 100) in place of
  the tree, with the transfer panel kept. Filters are session-only and cleared when another
  account signs in. The filter chip's look comes from the first database that styles the tag.
- **Display name** must canonicalise to the row's name (capitals and spacing only); a row from
  another client that breaks this is ignored by the renderer. Unknown colour keys render as
  `neutral`; colours reach the page only as palette hex values.
- **Palette.** neutral `#78716c`, red `#dc2626`, orange `#c2410c`, amber `#a16207`, green
  `#15803d`, teal `#0f766e`, violet `#7c3aed`, pink `#db2777`. Rules: 3:1 on `#ffffff` and
  `#151515`, ΔE ≥ 12 from primary, accent and each other, hue outside 200–260°. Gray candidates
  `#737373` and `#6b7280` failed ΔE against `--pn-primary`; stone-500 passes.
- **Chip shape.** `rounded-md`, 1 px border and 12 % tint in the colour, `#` glyph in the
  colour, name in the normal text colour (so its contrast never depends on the palette).
- **Phone.** Chips on Home and folder cards (read from the card's text with `readTagEntries`,
  coloured from its database; non-interactive because the card is a link); Settings → Tools →
  Tags opens the same manager; editor autocomplete works the same (tap a suggestion). No phone
  filter bar: filtering on a phone is search's `tag:` on the Search page (search spec phase 4).
- **Tools → Tags** opens on the selected Document's database; its state lives in `tagStore`,
  not `uiStore` (another agent edits `uiStore`).
- **Transfer step** copies only rows with a colour or display name, for copies and moves alike,
  and records `[]` when there was nothing to copy, so the step is never repeated.
